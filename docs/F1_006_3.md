## Scope and guarantees

`tools/activate_update.py` manages only a new directory within project `private/`.
No changes to the original preview, baseline, prepared candidate, browser localStorage, main branch or GitHub Pages. No publication permission. It does not convert a draft to verified.

- `init` copies the current web assets and the exact baseline bytes to `private/managed-preview/site/official.json`. The directory must not exist. Existing preview builds are untouched.
- `activate` checks complete DRAFT report, exact SHA-256 of current baseline and candidate, validates both datasets, reruns compatibility and audit, rejects new countback review cases; known unresolved cases may remain. Optional `--user` checks a supplied browser export. The export is never written to or served.
- Sporting content hash ignores only top-level `sources` and per-record `sourceIds`. All other fields, including dates, status, schedules, aliases, entrant and fastest laps, are compared. Array order is preserved (conservative: reordering may cause activation). Metadata-only changes are skipped; the original candidate/report retain fresh provenance. Empty report arrays alone are not used to decide a skip.
- On substantive changes, the active file is backed up under its SHA-256, a pending journal record is written and the candidate atomically replaces `site/official.json` using a same-directory temporary file and `os.replace`. Post-replacement checksum is checked. On caught write/verification errors the previous bytes are restored if needed; a failed restoration is reported and requires inspection. Failed prechecks never replace the file.
- Journal/backups are outside `site/`. A pending transaction is recovered from the actual active hash on the next invocation. A crash can leave `update.lock`; do not delete it until you confirm no activation process is running. After verifying the journal and active/backup hashes, an operator can remove that stale lock and run `status`. Unknown hashes block recovery. Not a power-loss durability or adversarial filesystem guarantee; external editing of managed files is unsupported.
- `rollback` requires explicit target backup SHA-256 and expected current SHA-256. The backup is validated before replacement; the current file is backed up too. Supply a current browser export when rolling back; without it browser predictions are not inspected, and predictions for removed future events can become temporarily unbound. Browser storage itself is not modified.
- The root lock excludes concurrent activation/rollback/status operations, not independent preparations. Stale prepared candidates are rejected by exact baseline hash. Keep using the active file as baseline for each new prepare run.

## Local commands (PowerShell at project root)

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
node --test tests/*.mjs
.\.venv\Scripts\python.exe tools/activate_update.py init --baseline private/f1db-all-f10033-reviewed.json
.\.venv\Scripts\python.exe tools/activate_update.py activate --run private/updates/run-001
.\.venv\Scripts\python.exe tools/activate_update.py status
.\.venv\Scripts\python.exe -m http.server 8765 --bind 127.0.0.1 --directory private/managed-preview/site
```

For run-001, expect `no_change` if sporting data (not merely report arrays) match. No new backup is created for a no-op. Keep the same browser profile, scheme, host and port to retain localStorage. Stop the old HTTP server first. Do not serve the entire private directory.

Optional: from Dashboard > My predictions export the browser backup and save as `private/user-browser-export.json`. Add `--user private/user-browser-export.json` to `activate` or `rollback` to validate that snapshot. No access to live browser storage; a current export is required to make this check meaningful.

Next update (choose a fresh run directory):

```powershell
.\.venv\Scripts\python.exe tools/prepare_update.py --baseline private/managed-preview/site/official.json --output private/updates/run-002
.\.venv\Scripts\python.exe tools/activate_update.py activate --run private/updates/run-002
```

For actual rollback, use hashes from `status`/journal, not sample values:

```powershell
.\.venv\Scripts\python.exe tools/activate_update.py rollback --sha256 BACKUP_SHA256 --expected-active CURRENT_SHA256 --user private/user-browser-export.json
```
